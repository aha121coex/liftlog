# LiftLog development contract

## Product requirements
LiftLog is a personal iPhone Home Screen PWA. Keep one-tap set completion fast and immediately saved without network dependencies. Recall each individual set's previous weight and reps, including ramp-up sets. Preserve exact manual input and independent exercise-specific lb/kg increments. Retain custom exercises, adjustable saved routines, recommendations, full history, progress, notes, timers and import/export. Let the user choose any session in either week even without prior logs. Suggest the next routine after the latest recorded plan key for the selected equipment, using the workout date/start time rather than history count or last edit time. Blank/custom/cardio sessions must not advance that rotation. Manual choices persist until a session with actual completed work is finished; never fabricate missed workouts. Switching an unfinished workout requires confirmation.

## Authoritative two-week home-gym program

The user supplied the full **STANDARD 2-WEEK HOME-GYM PROGRAM** in this conversation. `program.js` is its prescribed catalog: six training days per week in this order: Upper Push, Lower Push, Joint + Balance, Upper Pull, Lower Pull, Core + Carries; Day 7 is off. Each week has distinct prescriptions. `tests/program.test.cjs` independently transcribes all 76 exercise entries and their working-set ranges. Do not substitute the earlier three generic full-body workouts or invent exercise priority tiers absent from the supplied plan. Earlier gym A/B/C routines remain manually selectable; travel routines remain independent.

Use session order rather than a Monday reset. Allow any week/day to be chosen without inventing missing history. Recognize the new program only from its own `H1D1`–`H2D6` keys and actual completed entries; never relabel old A/B/C sessions. Keep the off-day guidance visible after Day 6 without enforcing calendar dates. Do not automatically truncate exercises for a time setting, add accessories, fill in prescribed cardio as completed, or queue make-up exercises from an unfinished session.

Working-set targets (`item.prescription`) are distinct from actual set values and status. Set `role` is `working` or `warmup`; optional `skipped` is incompatible with `done`. Pending entries become skipped only after explicit finish confirmation. Skip controls must never complete entries or affect progress; focus ignores skipped entries. Preserve skipped positions during recall so a later ramp-up/work set cannot slide into an omitted set's slot. Recall known warm-ups separately and keep the current session's working-set prescription even when the other week uses a different count. Legacy unlabelled extra sets are retained as editable references rather than silently guessed to be warm-ups.

Preserve all coaching notes, unilateral/per-side conventions, right-side-first hip/balance work, RPE/rest targets, symptom-based omissions, and the prohibition on step-downs. Loaded timed exercises (farmer carry and Pallof hold) need both weight and seconds; farmer weight is per hand. Preserve machine identity on entries, routines, backups and exports; never pool progress or recall loads across machines. Changing a machine after actual sets are logged requires a separate exercise entry. The two back-extension emphases and single-leg RDL variations have separate identities to avoid silently transferring loads from different movements.

Progression is explicit: reach every working set's upper rep bound with good technique at prescribed RPE, then use the smallest practical increase. Carries reach four 40-second rounds before increasing weight and returning toward 30 seconds. Do not infer technique/RPE or automatically increase loads from reps alone. The RDL's 15–25 lb reference is guidance, not a prefilled starting weight or a ceiling. The 10-minute hard finisher is 5 minutes building / 2 hard controlled / 3 easing, on stairs/bike/elliptical; no heart-rate target. See `PROGRAM_DESIGN.md` for compatibility and validation details.

Current user requirement: no cloud synchronization or Google OAuth setup. Keep workouts on the iPhone and provide user-initiated file sharing so ChatGPT can inspect a supplied snapshot. ChatGPT cannot directly reach private browser storage. Full backup sharing, short summaries and importing a returned routine are the supported exchange workflow. Do not add cloud infrastructure or promise automatic access without a new explicit request. Historical Google sync code and the experimental journal are dormant, retained in the repository for review only and excluded from the deployment artifact.

Preserve history across upgrades at the permanent GitHub Pages origin and `/liftlog/` path. Never require reinstalling, clearing site data or changing storage keys for an update. Backups, recovery, deletion and conflict resolution are product requirements, not optional maintenance.

## Cardio requirements and implementation

Read `CARDIO_DESIGN.md` before changing cardio. `cardio.js` supplies the Cardio view over the existing workout ledger, optional per-set `cardio` measurements and root `activityDays` manual step totals. These are additive schema-1 fields; do not duplicate cardio history into a second collection. Six-week volume and matched comparisons are derived, never saved as fabricated physiological data. The user wants standalone cardio and optional lifting finishers, outdoor jogs/dog walks, treadmill/stair-climber logging, and meaningful long-term trends. Separate activity volume, comparable performance benchmarks and sourced VO2 max estimates. Never infer VO2 max from steps or machine calories. Phone/watch integration is optional and requires an honest native HealthKit boundary; do not promise automatic Health access from this web app. Preserve existing history and avoid counting a linked session or daily steps twice.

## Current architecture
- `index.html`, `styles.css`: static mobile UI; deferred classic scripts.
- `program.js`: static 12-session prescription catalog, additional exercise definitions, prescription validation, role-aware recall helpers and explicit skip/machine/alternative actions. Loaded after `cardio.js` and before `app.js`; included in the verified offline shell. New fields are additive to schema 1.
- `app.js`: state, recommendations, rendering, delegated events, local persistence. Schema 1; primary key `liftlog.personal.v1`. History, exercises, templates, active session and settings are local. Active edits may share item/set IDs with a completed session.
- A browser Web Lock permits one editing window at a time. Other windows can download saved data and reload after the owner closes; browsers without Web Locks cannot edit. Reload state only after obtaining the lock. Primary localStorage saves synchronously. A serialized IndexedDB queue mirrors snapshots into `liftlog-offline-backup` / `snapshots` / `current`. Both stores share one browser failure domain. Neither is an independent backup.
- `sync.js`: legacy Google token client, canonical hashes and three-way comparison; five Sheet tabs: Workouts, Sets, Exercises, Routines, Routine Items. IDs are identity; row numbers are only temporary locators.
- Production sync is deliberately disabled in source. Neither the Google identity script nor the legacy sync runtime is loaded or shipped, and the Content Security Policy disallows external scripts and connections. Reopening sync requires a deliberate policy review as well as protocol tests. Do not remove these gates as routine cleanup.
- `sw.js`: SHA-256 verified, versioned shell cache pinned for each worker lifetime. An update waits for previous windows to close; never call skipWaiting during a workout. Run `python3 scripts/prepare-shell.py` after changing shipped assets; `npm run check` verifies hashes. Cache only declared assets within the registration scope. Never cache authenticated API responses or workout exports.
- No server or runtime package dependencies. Release preparation regenerates shell hashes with Python 3. `npm run build` creates the allowlisted `dist/` artifact. `.github/workflows/pages.yml` publishes main after tests; never include the repository wholesale in a Pages artifact. Node built-ins run automated tests.

## Development conventions
Read `SECURITY_REVIEW.md` before sync changes. Implement on a review branch and open a PR; do not merge or publish future changes without user direction. The user explicitly authorized completion and initial publication of the local-only 4.1 release in this session. Keep the existing UI and workout behavior. Make bounded changes with regression evidence. Run `npm run check` and `npm test`. Optional browser coverage: `python scripts/browser-smoke.py` (Python Playwright and `/usr/bin/chromium` required). Tests use synthetic records only. Add meaningful tests for failure cases, not just successful requests. Do not claim simulator checks establish iPhone reliability.

Keep schema migrations explicit, versioned, validated and reversible. Preserve raw unreadable storage before any recovery attempt. Never silently seed an empty database over failed parsing. The recovery screen pauses edits and permits raw-data download or explicit restore/reset. When the primary is missing, startup must finish checking the secondary before enabling edits. Restore validates before changing storage, saves the preceding raw database at `liftlog.personal.v1.beforeRestore`, aborts on write failure, and discards imported sync baselines/tombstones. This recovery slot is local and overwritten on the next restore; export independent backups before restoring. Do not merge backups by array position.

## Security constraints
Never commit personal workouts, exports, tokens, passwords, client secrets or service account keys. Public client IDs and Sheet IDs are identifiers, not authorization; avoid unnecessary personal identifiers. All GitHub Pages projects under the same account share an origin: their JavaScript can access the same localStorage and IndexedDB. Do not host untrusted applications under this origin. Consider a dedicated custom domain before enabling sensitive sync. Keep access tokens memory-only and short-lived. No refresh token in browser storage. Escape untrusted text at HTML boundaries; treat Sheet cells, imported JSON and routine names as untrusted. Write Sheet values as RAW to prevent formula execution.

Prefer `drive.file` with explicit file selection/grant for the intended Sheet. An ID hard-coded in JavaScript does not restrict a broad spreadsheets token. Test existing-file access with the real consent flow before adopting scope changes; never silently broaden scope to fix a 403. Keep exact authorized origins and account/Sheet confirmation in the design. Do not enable production authentication or reads/writes until least-privilege and data-integrity gates pass.

## Historical sync design (out of current scope)

See `SYNC_DEVELOPMENT.md` for the isolated journal prototype and integration gaps. `sync-protocol.js` is not production sync and must not be wired to the production Sheet before the release gates pass.
Use immutable operation IDs, stable entity IDs, durable outbox, explicit revisions, tombstones and a persisted device identity. Stage a snapshot; never acknowledge mutable live objects after awaiting network. Serialize local sync runs and detect concurrent devices/Sheet writers. Preserve both copies on conflicts and show their content before resolution. Missing rows are not deletion authorization. Retry after ambiguous timeout by reconciliation; never blindly append again. Parent/child writes require atomic commit or a recoverable transaction journal. Clear pending deletions only after verified remote acknowledgement. Preserve active sessions and exercise references when deleting library entries.

Before release, use a disposable private Sheet and synthetic data to test consent denial, expiry, revocation, wrong account/file, duplicate IDs, malformed rows, concurrent edits, deletion/edit conflicts, network loss at every write boundary, lost responses, reload/retry, restore with stale tombstones and edits during upload. Then test iPhone Safari and standalone mode, offline cold start, update during a workout, quota failure, interrupted persistence and backup round-trip. Record evidence and limitations in the PR. Production Sheet data must remain untouched during these tests.
