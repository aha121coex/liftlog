## Deletion and conflicts
Legacy code has explicit workout/exercise/template tombstone queues and set/routine-item tombstones. These are useful but not a reliable distributed protocol. Missing remote records become conflicts for existing local records; base-only IDs are not enumerated. Built-in exercises missing remotely are skipped. Exercise deletion already checked history and active sessions; this revision also protects references from saved templates. Reset removes local sync state and does not authorize remote deletion. A later reconnect may repopulate remote history. The current phone-delete wording understates eventual cloud tombstone propagation when sync is enabled. Conflict resolution offers labels without full side-by-side values and uses a potentially stale remote snapshot. These behaviors require explicit UI contracts and tests before production sync resumes.

## Backup and recovery
JSON is the complete backup format; CSV is for inspection, not full restore. Backup files contain private fitness history in plaintext. IndexedDB is a second local copy, not disaster recovery. Restore now validates before confirmation, preserves the previous raw database in a local recovery slot, writes replacement before adopting it in memory, and removes sync metadata. It still replaces rather than merges history. The recovery screen downloads the exact corrupt primary before restore. The data from before the last restore can be downloaded from More. Recovery slot rotation and automatic corrupt-primary recovery from the secondary remain future improvements. An unreadable secondary also pauses editing and permits its raw-data download instead of overwriting it with an empty database. Reset removes the recovery slot as well as replacing the primary and queued mirror. A successful file download is not proof that a backup can restore: test round trips on another disposable browser profile.

## Public exposure and deployment
The repository is public and includes a Sheet ID. Unnecessary account email and legacy production-enablement instructions were removed from the working documentation. A limited signature scan over 12 unique blobs across all three upstream commits found no private-key, GitHub-token, Google access-token or Google client-secret pattern. No evident credential literal was found in reviewed source; this is not proof that credentials were never exposed. Do not publish backups or private Sheet samples. OAuth client ID is public by design. If a secret is found later, revoke it first; deleting its current file is insufficient. Repository metadata reported `has_pages: false` and the authenticated Pages API returned 404; no hosting configuration was changed. The user subsequently authorized initial publication of the local-only release. The publishing workflow deploys an allowlisted static artifact; none of the historical Google sync code, tests, docs or backups are shipped.

## Release gates and validation limits
Node tests cover blocked production entry points, nested backup rejection, duplicate identities, exact per-set recall, active-edit ID reuse, quota failures, both restore write failure boundaries, stale sync intent, reset, startup recovery, IndexedDB aborts, unit conversion and exercise references. Worker tests reject mixed-version assets and verify pinned cache responses. Syntax checks cover all runtime JavaScript. CI runs these checks with read-only repository permissions. The Chromium smoke script passed a touch viewport, manual weight entry, one-tap local saving, reload, offline shell/logging, downloaded JSON round-trip, IndexedDB recovery and corrupt-primary recovery. Browser coverage also verifies a blocked competing window and transfer of the writer lock after the owning window closes. The lock protects participating versions; close all legacy v4 windows before upgrading. These checks do not verify real Google authentication, Sheet concurrency, all browser UI flows or physical iPhone lifecycle behavior. Follow the disposable-Sheet and iPhone matrix in AGENTS.md before enabling any production sync. Do not simply flip the gate: legacy sync defects remain intentionally documented and quarantined.

The page also has a restrictive Content Security Policy (same-origin scripts and connections, no embedded objects or form submission) and no-referrer policy. This reduces exposure but does not substitute for data validation, origin isolation or OAuth testing.

## Local cardio release

The 4.3 cardio module projects existing workout entries into a separate Cardio view, retaining stable session/item/set identities. It does not create a second history copy. New optional per-set measurement objects and daily manual step totals are validated before restore. Fitness daily totals replace the same date and are not incremented by individual walks. Cardio-only entries leave lifting rotation unchanged; a separate completed activity can be logged without discarding an active lift.

No HealthKit, Apple Fitness or wearable connection is claimed or enabled. Missing heart rate and other measurements remain unknown; duration recall does not copy old actual heart rate, distance or effort into new sessions. Comparisons separate activity, named route/machine, entered workload, measurement source and lifting context. The charts show activity/performance rather than an inferred VO2 max. Optional measurements are included in user-initiated JSON sharing and backups; they are never part of the published artifact or sent to a cloud service by LiftLog.
